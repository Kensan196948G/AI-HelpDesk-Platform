## 1. 実装した 3 点

### 1-1. 手順の繰り返し試行の一覧・試行済み表示（② 運び役・AI一次対応）

`apps/api/src/prototype/kb-trial-bridge.js`

- チャットの直後に「候補の手順（n件）」を差し込む。会話が流れても常に一覧が見える。
- 一覧は次の和集合（重複なし）。ローカルの保存領域（`mirai-wizard-v31-helpdesk`）の案件から作る。
  - 表示中の手順（`activeKb`）
  - 候補（`candidates`）
  - これまで提示した手順（`shown`）
  - 試行して解決しなかった手順（`failedKb`）
- 表示: **表示中** / **試行済み**（表示中のものが試行済みなら「前回は解決せず」）/ **使用停止**。近さは候補提示メッセージの値を出す。
- 並び: 表示中 → 未試行 → 試行済み。近さの高い順。最大 8 件。
- 「この手順を試す」は既存の `App.pickCand` を呼ぶ（提示・保存の処理を二重実装しない）。
- **制約**: 原本の `App.pickCand` は「候補の提示」メッセージがあるときだけ動く（無いと内部で例外）。そのため一覧に切り替えボタンを出すのは候補提示がある場合だけにし、無い場合は「AIに『別の方法を教えてください』と送ると候補が出ます」と案内する。**この制約は画面にも明記**している。
- 問い合わせが対応中・完了のときは、一覧は表示のみ。

### 1-2. AI検査・指摘（⑤ ナレッジ下書き）

`apps/api/src/prototype/knowledge-review-bridge.js` ＋ `POST /api/knowledge/inspect`

- ⑤ の下書きフォームの下に「AI検査・指摘」パネルを足す。ボタンで現在の入力内容をサーバーへ送り、指摘と**参考スコア**を表示する。
- 検査規則は**保存時の伏せ字（`redactKnowledgeText`）と承認時の端末情報検査（`containsDeviceInfo`）と同じ正本**。新しい規則は作っていない。
- 表示する項目（7 件）: タイトル・症状・原因・手順の有無と長さ、個人情報・端末情報の残り（保存時に伏せ字）、保存後の本文が承認時の検査に通るか、キーワードの件数・長さ・端末情報。
- 点数の目安: 100 点から、必須項目の欠落（-20/-10/-10/-20）、伏せ字の種類（1 種類 -6、最大 -18）、保存後の端末情報（-25）、キーワード（-5）を引く。**点数は参考で、承認の可否は決めない**（画面にも明記）。
- 「伏せ字にした後の本文を確認」で、保存時にどう伏せられるかを開いて見られる。
- **自動修正は行わない**（画面にも明記）。サンプルの「2項目は自動修正」は採らない（docs/92 §3-1 #4 の「指摘表示」に限定）。

### 1-3. 承認ボタンの制御・チェックの進捗（⑥ 承認者の確認）

`apps/api/src/prototype/knowledge-review-bridge.js`

- チェックリストの上に「確認の進捗 n/4」とバーを出す。4/4 で「すべて確認しました」。
- 4 項目そろうまで承認ボタンを無効にする（薄く表示し、理由を `title` に出す）。
- 無効にするのは**表示の制御だけ**。承認の正当性の検証は従来どおりサーバー側（`App.approve` の確認と、`ui-sync` の承認検査）で行う。
- もともと権限が無くて無効なボタン（承認者でない・申請者本人）は、こちらの制御では**有効にしない**（自分が付けた無効だけを戻す）。
- 画面の再描画後も進捗と無効を付け直す（DOM の変更を監視）。
- サーバー下書き一覧（assist-bridge の「サーバ下書き（承認待ち）」）は、従来から 4 項目がそろうまで承認ボタンが押せない。今回の変更は ⑥ のローカル下書きのパネルが対象。

## 2. 追加した API

`POST /api/knowledge/inspect`（読み取り専用）

| 項目 | 内容 |
|---|---|
| 認証 | `authenticateUi`（UI セッション）＋ ヘルプデスク相当（`requireHelpdeskActor`） |
| 入力 | `title` / `symptom` / `cause` / `steps`（文字列）、`keywords`（文字列の配列）。上限は保存より緩くし、長すぎる場合も指摘として返す |
| 出力 | `score`（参考）、`maxScore`、`reference: true`、`redactions`（伏せ字の種類と件数）、`blocking.deviceInfo`（保存後の本文で承認時の検査に通るか）、`items`（7 項目の合否）、`redacted`（伏せ字後の本文） |
| DB | 読まない・書かない |
| 監査 | 残さない（読み取り専用で状態を変えないため） |
| 登録順 | `/knowledge/:id` より前に登録（`inspect` が ID として解釈されないように） |

### 4-2. UI スモーク（スクリーンショット）

原本 HTML にブリッジを差し込んだ**スタンドアロンのハーネス**（API・DB・認証なし）で、ブラウザ（Playwright）により実操作した。案件・下書きは件名に「（UIスモーク）」と明記した検証用データだけを使う。

| 画像 | 内容 |
|---|---|
| `docs/evidence/knowledge-review/02-ai-candidates.png` | ② の候補一覧（表示中・使用停止・試行済み・切り替え） |
| `03-draft-inspect.png` | ⑤ の AI検査・指摘（参考スコア 76/100、✓/✗、伏せ字の予定） |
| `04-approve-0of4.png` | ⑥ の進捗 0/4。承認ボタンは無効（薄く表示） |
| `05-approve-4of4.png` | ⑥ の進捗 4/4。バーが満杯になり、承認ボタンが押せる |

実測したこと:

- 一覧は 3 件（表示中 1・試行済み 1・使用停止 1）で、並びは 表示中 → 未試行 → 試行済み。
- 「この手順を試す」で `activeKb` が切り替わり、会話に新しい手順が追加され、一覧の「表示中」も移動した（localStorage の `activeKb` で確認）。
- 検査は参考スコア・7 項目・伏せ字後の本文を表示し、エラーにならない。
- ⑥ は 0/4 で承認ボタンが `disabled`、4/4 で `disabled` が外れてバーが 100% になった。再描画後は 0/4 に戻り、無効が付け直された。
- 承認者でない操作者では、チェックリストも承認ボタンも無効のまま（こちらの制御で有効にしない）。

**限界（未検証）**:

- 実サーバ（API・DB・Cloudflare Access）での操作は未実施。ハーネスでは検査 API を固定応答に差し替えている（画面の表示の確認であって、実 API の応答の確認ではない）。
- `POST /api/knowledge/inspect` は、検査の純粋関数を単体試験で確認した。経路そのもの（認証・入力検証）の実サーバ試験は追加していない（CI の既存試験の範囲）。
- 原本の `App.pickCand` の制約（候補提示メッセージが必要）は残っている。ブリッジ側で案内を出し、無理に代替実装はしていない。
- サーバー下書き一覧の進捗表示は対象外（従来からボタンの無効化はある）。

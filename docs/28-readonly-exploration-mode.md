# 読み取り専用の探索モード（設計）

| 項目 | 値 |
|---|---|
| 版 | v0.1（設計・実装なし） |
| 作成 | 2026-10-25 |
| 背景 | [27-solution-gap-measurement.md](27-solution-gap-measurement.md)：変更系 Skill 0 件、端末実行 0 件、verify/rollback 0 件 |
| 位置づけ | 非スコープ（`docs/25` §1-3「AI が任意の PowerShell を生成して実行する」）の**精密化**。禁止は維持したまま、読み取りの自由度だけを上げる |

---

## 1. なぜ必要か

実測（`docs/27`）で分かったのは、AI が「用意された 5 つの質問」しか端末に投げられないこと。しかも 5 件はすべて read-only で、KB 9 件のうち端末状態を取れるのは 3 件だけだった。

利用者が感じる「賢くない」は、**質問できる幅の狭さ**に由来する。読み取りには本質的にリスクが小さいのに、書き込みと同じ承認モデルに縛られているため、探索ができない。

一方で、`docs/25` の非スコープは正しい。**AI に任意のコマンド文字列を書かせて実行させる**のは、この製品ではやってはいけない（承認ハッシュの意味が消える）。

したがって本設計は「自由化」ではなく **「読み取りプリミティブの拡張と連鎖」** とする。

---

## 2. 設計原則

| # | 原則 | 内容 |
|---|---|---|
| P1 | **AI はコマンド文字列を生成しない** | 生成するのは `primitiveId` + 型付きパラメータのみ。文字列連結・シェル展開を経由しない |
| P2 | **読み取り専用は型で保証する** | プリミティブは「一覧・状態・件数」のみ。ファイル内容・レジストリ値・画面・キー入力を返さない |
| P3 | **変更は従来どおり承認必須** | 探索モードは `resolution_steps` を 1 つも `approved` にしない。変更系 Skill の経路は不変 |
| P4 | **探索は上限つき** | 1 セッションあたり最大 4 プリミティブ、各 15 秒、出力 32KB。超過は探索終了 |
| P5 | **全実行を監査** | 既存のハッシュチェーン監査に `explore.executed` を追記 |
| P6 | **出力はデータとして扱う** | 端末出力に含まれる文字列を指示として解釈しない（既存 system prompt の方針を維持） |

---

## 3. プリミティブ（10 件・すべて読み取り専用）

`skills` テーブルに `risk_level=1`、`verify` = 「取得できたこと」、`rollback` = `null`（変更しないため）で登録する。承認は既存のハッシュ承認に載せる。

| id | 返すもの | 主要パラメータ | 明示的に返さないもの |
|---|---|---|---|
| `diag.process.top` | CPU/メモリ上位プロセス（名前・使用率・PID） | `top` (1-20) | コマンドライン引数、実行パス |
| `diag.service.query` | 指定サービスの状態・起動種別 | `names[]`（最大 10） | — |
| `diag.eventlog.errors` | 直近のエラー/警告イベント（件数・ID・時刻・ソース） | `hours` (1-72), `max` (1-50) | メッセージ本文の全文（先頭 200 字まで） |
| `diag.network.probe` | 名前解決・到達性・遅延 | `host`, `port?` | — |
| `diag.network.config` | アダプタ・IP・GW・DNS（マスク済み） | なし | MAC アドレス |
| `diag.disk.usage` | ボリューム別の容量・空き | なし | ファイル一覧 |
| `diag.software.list` | 導入ソフト（名前・版） | `nameFilter?` | ライセンスキー |
| `diag.update.status` | 更新の適用待ち・再起動要否 | なし | — |
| `diag.defender.status` | 保護状態・定義版・最終スキャン | なし | 検知名・パス |
| `diag.bitlocker.status` | 保護状態・暗号化方式 | `mount?` | **回復キー（絶対に返さない）** |

> 追加・変更は「読み取り専用であること」をレビューで確認したうえで、既存の承認フローに載せる。

## 4. 実行フロー

```
[相談文 + PC基本情報 + これまでの探索結果]
        │
        ▼
[AI: 診断計画]  { primitiveId, params, rationale }  ※コマンド文字列は生成しない
        │
        ▼
[サーバ: 検証]  ・primitive が許可リストに存在
                ・params が JSON Schema に適合（additionalProperties:false）
                ・探索回数 < 4、セッションが active
                ・risk_level = 1 であること（2 以上は通常の承認経路へ）
        │
        ▼
[端末エージェント]  固定 .ps1 に -Param で明示バインド（文字列連結なし）
                    ・ConstrainedLanguage モード
                    ・15 秒タイムアウト、出力 32KB 上限
        │
        ▼
[出力ポリシー]  許可フィールドのみ抽出 → PII マスク → 32KB に切詰め
        │
        ▼
[監査]  explore.executed { primitiveId, paramsHash, durationMs, ok }
        │
        ▼
[AI: 結果を評価] → 次のプリミティブ / 変更系 Skill の提案 / 引継ぎ
```

**承認 Y/N は探索には出さない。** 代わりにセッション開始時に一度だけ「端末の状態を読み取ってよいか」の同意を取る（現行の PC 情報収集と同じ扱い）。

## 5. 非スコープの再定義（`docs/25` §1-3 の改訂案）

| 現行 | 改訂案 |
|---|---|
| AI が任意の PowerShell を生成して実行すること | AI が任意の PowerShell **文字列**を生成して実行すること（**変更を伴う操作は引き続き禁止**） |
| — | 追加: AI が**登録済みの読み取り専用プリミティブ**を、型付きパラメータ付きで選択・連鎖することは許可する |
| — | 追加: プリミティブの追加は code review + 人間承認を要する。`verify` が「取得できた」であることを必須とする |

この改訂により、禁止の核心（AI が自由なコマンドで端末を変更できる）は維持される。

---

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 読み取り経由の情報漏えい | 中 | 返すフィールドを固定。ファイル内容・レジストリ値・回復キーは型で排除。PII マスクを通過 |
| 端末出力へのプロンプト注入 | 中 | 出力はデータとして渡す。プリミティブの出力に「指示」を含むフィールドを設けない |
| 大量イベント取得による端末負荷 | 低 | `hours`/`max` の上限、15 秒タイムアウト、出力 32KB |
| 探索の無限ループ | 中 | 最大 4 回。同一プリミティブ + 同一パラメータの再実行は拒否 |
| 探索結果を根拠にした誤った変更提案 | 中 | 変更は従来どおり承認ハッシュ必須。探索結果は `rationale` に引用させる |
| ConstrainedLanguage の回避 | 低 | 端末エージェント側で実行ポリシーと許可リストを強制。未知 primitive は fail-closed |

## 7. 期待される効果（実測との対応）

| 指標 | 現状（`docs/27`） | 探索モード後（設計上の上限） |
|---|---|---|
| 端末状態を取れる KB シナリオ | 3 / 9 | 9 / 9（0007・0008 を含む） |
| AI が端末操作で解決まで到達できる件数 | 0 / 9 | Phase 2 の修復 Skill に依存（0003・0004・0005） |
| 診断止まり率 | 測定不能（実行 0 件） | 30 件評価セットで測定 |

探索モードは**診断の天井を上げる**が、**変更の天井は上げない**。変更は Phase 2（修復 Skill）と人間承認が担う。

---

## 8. 実装順序（提案）

1. プリミティブ 10 件の `.ps1` と定義（`skills` へ `draft` で登録）
2. サーバ側の検証（許可リスト・スキーマ・回数上限）と監査イベント
3. 端末エージェントの許可リストとタイムアウト・出力上限
4. 画面の同意 UI と探索結果の表示（「何を確認したか」を利用者に見せる）
5. 30 件評価セットで before/after を測定

> 1〜3 は既存の解決ループの仕組みをそのまま使える。新しい実行基盤は不要。

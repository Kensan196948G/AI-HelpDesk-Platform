# 解決能力ギャップの実測（2026-10-25）

| 項目 | 値 |
|---|---|
| 目的 | 「AI の解決能力が低い」という体感を、実データで分解する |
| 対象 | 稼働中 API（`ai-helpdesk-api.service`）が使う DB = `ai_helpdesk_preview` |
| 方法 | 読み取り専用（`SET default_transaction_read_only = on`）で集計。接続文字列・ホスト・利用者は出力していない |
| 結論 | **解決ループは実運用で 1 回しか動いておらず、端末コマンド実行は 0 件。履歴からの失敗分類は不可能。** 代わりに「構造カバレッジ」を実測した |

---

## 1. 実測結果：判定に使える履歴が存在しない

### 1-1. 件数（実測）

| テーブル | 件数 | 備考 |
|---|---|---|
| `resolution_sessions` | **1** | 状態 `stopped`、`step_count=1` |
| `resolution_steps` | **1** | 状態 `cancelled`（提案されたが実行されず中止） |
| `device_commands` | **0** | **端末コマンドは一度も実行されていない** |
| `cases` | 3 | 固定 UUID（`c0000001`…）＝シード |
| `tickets` | 3 | 同上 |
| `resolutions` | 1 | 同上 |
| `case_messages` | 9 | 同上 |
| `knowledge` | 9 | KB-2026-0001 〜 0009、全て `approved` |
| `audit_log`（resolution 系） | 3 | `session_started` / `proposed` / `stopped` が各 1 |

`audit_log` には `seed_demo_data` が 1 件だけ存在する。**つまり DB の中身はシードと、中止された 1 セッションのみ**である。

### 1-2. これが意味すること

- `resolution.escalated` は **0 件**。`reason`（`no_skill` / `no_progress` / `step_limit`）による分類は**実行できない**。
- 端末コマンド実行が 0 件なので、「実行したが直らなかった」（モード C）も**観測できない**。
- 画面に出ていた「AI自己解決率 33%」は `cases.ai_resolved` / `tickets` のシード値であり、**解決ループの成果ではない**（別経路の集計）。

> したがって「A が 7 割」といった推定は、現時点では**データに基づかない**。本ドキュメントでは推定を断定しない。

---

## 2. 代替実測：静的な能力カバレッジ（KB 9 件 × 現行 5 Skill）

履歴が無い以上、測れるのは「**このシステムは、既知の 9 シナリオに対して何ができるか**」である。KB の `steps` を読み、解決に必要な操作の種類で分類した。

| KB | 症状 | 解決に必要な操作 | 現行 Skill | 操作種別 | AI が到達できる終点 |
|---|---|---|---|---|---|
| 0001 | 共有フォルダ アクセス拒否 | セキュリティグループ追加（申請） | なし | 人間 | 担当者へ |
| 0002 | Teams 音声出力先 | 利用者が設定変更 | なし | 利用者 | 案内で解決可 |
| 0003 | 印刷ジョブが消えない | ジョブ削除＋スプーラ再起動 | `spooler.status`（読取） | **変更** | **診断止まり** |
| 0004 | VPN につながらない | 再接続・アダプタ確認 | `network.adapters`（読取） | **変更** | **診断止まり** |
| 0005 | PC が重い | 負荷確認・一時ファイル整理 | `os.info` / `disk.space`（読取） | **変更** | **診断止まり** |
| 0006 | Windows Update 再起動待ち | 再起動（作業影響大） | なし | 人間/利用者 | 案内 |
| 0007 | BitLocker 状態確認 | `manage-bde -status`（読取） | なし | 読取 | **案内のみ**（端末状態を取れない） |
| 0008 | Defender 状態・スキャン | 状態確認＋クイックスキャン | なし | 読取/変更 | **案内のみ** |
| 0009 | ソフト導入 | 導入申請 | なし | 人間 | 担当者へ |

### 2-1. 集計（実測）

| 指標 | 値 |
|---|---|
| KB シナリオ数 | 9 |
| **端末を変更して解決しうるシナリオ** | **3**（0003 / 0004 / 0005） |
| そのうち**現行で変更操作が可能な件数** | **0** |
| 端末の読み取りで解決しうるシナリオ | 2（0007 / 0008） |
| そのうち**現行で読取 Skill がある件数** | **0** |
| 利用者操作・人間手続きで解決するシナリオ | 4（0001 / 0002 / 0006 / 0009） |
| **AI が端末操作で解決まで到達できる KB シナリオ** | **0 / 9** |

### 2-2. Skill の契約状態（実測）

```
skills: 5 件 / 全て status=approved / risk_level=1
        has_verify = false（全件）
        has_rollback = false（全件）
        timeout_sec = 60（全件）
```

**全 Skill に `verify` と `rollback` が無い。** 読み取り専用だから今は破綻していないが、変更系を追加した瞬間に「実行したが直ったか判定できない」「失敗時に戻せない」という穴になる。**Phase 2 の前提条件**である。

---

## 3. 失敗モードの割り当て（推定ではなく構造から）

履歴が無いため、モードは「発生しうる構造」として割り当てる。

| モード | 定義 | 現状の該当 | 根拠 |
|---|---|---|---|
| **A. 手順が無い** | 診断はできるが、変更する手順がカタログに無い | KB 9 件中 **5 件**が端末操作先を持たない（0001/0006/0007/0008/0009） | §2 の表。変更系 Skill 0 件 |
| **B. 選べない** | 手順はあるが選定を誤る | `proposer.ts` の fallback は 5 ルール（印刷・容量・ネットワーク・OS・サービス） | 曖昧入力では `no_skill` |
| **C. 直ったか分からない** | 実行後の検証・巻き戻しが無い | **全 Skill で verify/rollback が NULL** | §2-2 |
| **D. 知識が無い** | KB 外の相談 | 9 件でカバー。それ以外は仕様どおり引継ぎ | KB 9 件 |

**A と C は「能力」ではなく「実装の欠落」**である。モデルを替えても、ハーネスを替えても、ここは 1 件も改善しない。

---

## 4. 結論

「AI の解決能力が低い」の実体は、次の 3 つに分解できる。

1. **変更できる手順が 0 件**（`device_commands` 実行実績も 0 件）。AI は診断して「担当者へ」と言うしかない。
2. **検証と巻き戻しの契約が 0 件**。将来変更系を足しても、直ったか判定できない。
3. **ループ自体が実運用で使われていない**（1 セッション、中止）。使われていないものは改善も測定もできない。

したがって優先順位は「モデル/基盤の交換」ではなく、**(a) 変更系 Skill の追加、(b) verify/rollback の必須化、(c) 評価セットによる継続測定**である。

## 5. 次回の測定設計（30 件評価セット）

履歴が無いため、測定は**能動的に流す**しかない。以下を次回の実行条件とする。

### 5-1. 実行条件（安全側）

| 項目 | 条件 |
|---|---|
| DB | **専用の検証 DB**（`ai_helpdesk_verify_*`）。preview/production には書き込まない |
| ゲート | 既存の `AIHD_E2E_CONFIRM_DB` と同様に、DB 名の完全一致を接続前に検査 |
| API | 別ポートで起動。`AUTH_MODE=local`、`DEV_AUTH_EMAIL` は検証用 |
| AI | 課金上限を決めてから実行（1 ケース 1 リクエスト、リトライなし） |
| 出力 | ケース ID・成否・停止理由・到達状態のみ。相談文はログに出さない |

### 5-2. ケース構成（30 件）

| 区分 | 件数 | 内容 | 期待する終点 |
|---|---|---|---|
| KB 直球 | 9 | KB-0001〜0009 の症状文そのまま | 案内 / 修復 / 引継ぎ |
| KB 言い換え | 9 | 同じ症状を利用者の言葉で（専門用語なし） | 同上（選択精度の測定） |
| KB 境界 | 6 | 2 つの症状が混在（例: 印刷＋PC重い） | 誤選択しない |
| KB 外 | 3 | 経費精算・権限付与・機器故障 | 推測せず引継ぎ |
| 敵対 | 3 | プロンプト注入・個人情報・スコープ外 | 拒否・マスク・引継ぎ |

### 5-3. 記録する指標

- **解決率**（`resolved` に到達 / 全ケース）
- **診断止まり率**（`done` したが変更なしで終了）
- **モード別内訳**（A: `no_skill` / B: 誤選択 / C: 実行失敗 / D: 引継ぎ）
- **誤選択率**（期待 Skill と提案 Skill の不一致）
- レイテンシ p50/p95

> 分母を 30 件に固定し、Phase 2 の前後で同じセットを流す。これが無い限り「良くなった」は言えない。

## 6. 再現手順

```sql
-- 稼働中サービスと同じ DB に、読み取り専用で接続する。
SET default_transaction_read_only = on;

SELECT 'resolution_sessions', count(*) FROM resolution_sessions
UNION ALL SELECT 'resolution_steps', count(*) FROM resolution_steps
UNION ALL SELECT 'device_commands', count(*) FROM device_commands
UNION ALL SELECT 'cases', count(*) FROM cases
UNION ALL SELECT 'knowledge', count(*) FROM knowledge;

SELECT status, count(*) FROM resolution_sessions GROUP BY 1;
SELECT action, detail->>'reason', count(*) FROM audit_log
 WHERE action LIKE 'resolution.%' GROUP BY 1,2;

SELECT id, risk_level, (verify IS NOT NULL) AS has_verify,
       (rollback IS NOT NULL) AS has_rollback, status
  FROM skills ORDER BY id;
```

接続文字列はサービスの実行環境から取得し、**値は表示しない**（`DATABASE_URL` を出力しない）。

# 99. WebUI のログアウト（Cloudflare Access のセッション終了）（2026-11-11）

## 0. 結論

画面右上の「プロフィール」の隣に **「ログアウト」** を足した。押すと **Cloudflare Access のセッションを終える**ため、同じブラウザで**別のアカウントにログインし直せる**。

- 原本 HTML は変更しない（実行時にボタンを 1 つ足すだけ）。追加は **ブリッジ 1 本**と boot の 1 項目、試験、文書。
- これまで画面にログアウトが無く、アカウントを切り替えるには**プライベートウィンドウ**を使う必要があった（2026-11-11 の本番受入で実測）。その手間を無くす。

## 1. なぜ必要だったか

- 本番の承認は**職務分離**のため、自分が引き受けた案件は同じメールでは承認できない（`SELF_APPROVAL_FORBIDDEN`）。受入の片付けで「別アカウントでの承認」が必要になったが、**画面にログアウトが無く**、Access の SSO セッションが残るため切り替えられなかった。
- 画面の「操作する人」は**表示とローカルの状態を切り替えるだけ**で、サーバの本人判定（Access のメール）は変わらない。承認の代替にはならない（誤用を避けるため、この違いは [docs/98](98-deploy-webui-20261111.md) §7-2 と本 doc に明記する）。

## 2. 実装

### 2-1. 画面（`apps/api/src/prototype/logout-bridge.js` を追加）

- ヘッダーの `button[data-act="profile"]`（プロフィール）の**直後**に、同じ見た目（`u-pill`）の「ログアウト」を 1 つだけ足す。CSS は足さない。
- 押すと確認ダイアログを出し、**何が起きるか**を先に示す。
  - Access: 「Cloudflare Access のセッションが終わり、別のアカウントでログインし直せます」
  - ローカル開発: 「ログアウトします（ローカル開発）」
- 遷移先は **boot の `authMode` だけで決める**（画面から認証方式を推測しない）。
  - `cloudflare-access` → `/cdn-cgi/access/logout` へ遷移（Cloudflare がエッジで受けるため、ローカル proxy や API には届かない）
  - `local` → `POST /api/auth/logout` を試し、成否に関わらず再読み込み
- **想定外・欠落した値はローカル扱い**（本番の Access セッションを誤って切らない安全側）。
- 画面の状態（`localStorage`）はこのブリッジでは消さない。**ログインしたメールが変わったとき**、配信時の boot スクリプト（`apps/api/src/routes/prototype.ts`）が既存の状態を破棄する（従来の挙動）。

### 2-2. 配信（`apps/api/src/routes/prototype.ts`）

| 変更 | 内容 |
|---|---|
| `BRIDGE_FILES` | `logout-bridge.js` を追加（全画面に配信） |
| boot | `authMode: config.AUTH_MODE` を追加（`local` / `cloudflare-access`） |

## 3. 使い方（アカウントの切り替え）

1. 画面右上の「**ログアウト**」→ 確認で「OK」
2. Access のログアウト画面になる → アプリの URL を開き直す
3. ログイン画面で**別のメール**を入力 → 届いた 6 桁コードでログイン
4. 画面の状態は**メールが変わった時点で破棄**される（前の人の案件・下書きは引き継がない）

## 4. 検証

| 試験 | 結果 |
|---|---|
| `npx vitest run --config vitest.pure.config.ts` | **12 ファイル / 334 件 成功**（うち `logout-bridge.test.ts` 8 件を追加） |
| `npm run typecheck` / `npm run lint` | 成功（CI で再確認） |
| 画面での実測 | 配備後に確認（本 doc 追記） |

追加した試験（8 件）:

- Access では `/cdn-cgi/access/logout` へ遷移、ローカルでは `POST /api/auth/logout`
- boot が無い・`authMode` が想定外 → **ローカル扱い**（Access を切らない）
- 確認文が Access では「セッションが終わる」「別のアカウントで入り直せる」ことを伝える
- `localStorage` を消さない（状態の破棄は配信側の責務）
- ボタンは 1 つだけ（二重マウントしない）／画面用のデモデータを持たない

## 5. 限界

- **IdP（外部の SSO）からのログアウトはしない**。Access のセッションを終えるだけ（本番はワンタイム PIN なので IdP セッションは無い）。
- `local` モードの `POST /api/auth/logout` は既存のセッション認証向け。ローカル開発では元々 Access セッションが無いため、実質は再読み込み。
- 画面の状態（`localStorage`）はログアウト時点では残る。**別メールでログインするまで残る**（同じメールで再ログインした場合は従来どおり復元される）。
- 動作確認は**配備後**に行う（本 doc の §4 に追記する）。

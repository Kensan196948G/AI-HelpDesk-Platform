## 1. 目的

引継ぎ後に担当者が「次に何をするか」を 1 画面で判断できるようにする。
既存の「③ 引継ぎ・④ 解決記録」は情報が 1 列に並ぶため、引継ぎメモ・会話・
案件情報・記録を行き来しやすい。3ペインで次の順に固定する。

- **左**: 引継ぎボード（未受領の引継ぎ、引継ぎ待ち、対応中、解決）
- **中**: 案件の経過と「次の一手」（担当開始 / 解決記録 / 解決済み）
- **右**: 案件情報、端末・共有情報、AI操作の承認記録、関連ナレッジ、監査

## 2. 起動と閉じ方

- ヘルプデスク画面（`S.ui.screen === 'tool'` かつ `S.ui.view` が `h.*`）でのみ、
  右下に「🧭 引継ぎワークスペース」ボタンを表示する（追加 DOM。既存レイアウトは変えない）。
- 左ナビ（`#uxRail`）にも「引継ぎ」を追加する（一般社員には非表示）。
  `uxShell` の再描画で消えるため `MutationObserver` で戻す。クリックで同じ画面を開く。
- クリックすると、既存の右側コンテンツ（`.ux-content`）内に表示する。
  左ナビとアプリのヘッダーは残る。**別ウィンドウ（`window.open`）ではない**。
- 表示中は `.ux-content` の `#uxPage` / `#cw` / `#hd` を隠し、`#ahd-hw` を
  flex 子として同じ領域に表示する。閉じる・別ナビへの移動で元の画面に戻る。
- `.ux-content` が無い場合だけ、従来の全画面オーバーレイにフォールバックする。
- 閉じる: `Esc`、または左ナビの「引継ぎ」をもう一度押す（別ナビへの移動でも閉じる）。
  インライン表示では右上の「×」を出さない。全画面オーバーレイにフォールバックした場合だけ表示する。
- 画面を閉じても既存の操作・状態は変わらない（読み取り＋明示操作のみ）。

## 3. 画面の内容

### 3-1. 左ペイン（引継ぎボード）

- 未受領の引継ぎ（`GET /api/case-handovers/inbox`）を最上部に表示し、「引き受ける」で claim。
- 既存チケットのうち `escalated` / `in_progress` と、直近 7 日の `resolved` を表示。
- 並び: 引継ぎ待ち → 対応中 → 解決、その中で優先度（P1〜P4）→ 期限。
- 絞り込み（すべて / 引継ぎ待ち / 対応中 / 解決）と検索（案件番号・件名・依頼者・端末）。
- カードには優先度、状態、担当、SLA（残り / 超過）、AI窓口由来か、セキュリティ事象かを表示。

### 3-2. 中央ペイン（経過と次の一手）

- ヘッダー: 件名、案件番号、優先度、状態、依頼者、受付、期限、担当。
- **次の一手**を最初に表示する。
  - `escalated`: 担当者を選び「担当して対応開始」。
  - `in_progress`: 原因・手順・所要・備考・ナレッジ下書きの有無を入力し「解決を記録」。
  - `resolved`: 解決記録の内容とナレッジ下書きへの導線。
- **AI に聞く**: 質問を入力して AI の回答を得る。AI窓口由来の案件は
  `POST /api/ai/answer-case`（共有 PC 情報と AI 一次対応の履歴を根拠）、
  直接受付の案件は `POST /api/ai/answer`（承認済みナレッジを根拠）を使う。
  回答・根拠 KB・モデル・確信度を表示する。
- 「AIによる引継ぎメモ」（既存の `buildHandover` の全文）。
- 問い合わせ内容。
- AI相談の会話（AI窓口から引き継がれた案件で、cowork 状態に会話がある場合）。
  ない場合は既存の `aiLog`（AI一次対応の記録）を表示。
- 対応タイムライン（既存の `history`）。

### 3-3. 右ペイン（案件情報・記録）

- 案件情報（状態、優先度、受付、期限、担当、分野）。
- 端末・共有情報（`coworkShared`。本人が同意した範囲のみ）。
- AI操作の承認記録（引き継ぎ元の cowork 状態に提案がある場合）。
  **既存の修復フロー（承認ハッシュ）の記録**であり、解決ループ（Skill / verify）とは別系統。
- 関連ナレッジ（`kbId` / `failedKb` / AIログ・関連付けの KB）。
- ナレッジ下書きの状態と導線。
- 操作の記録（ヘルプデスクの監査ログ。対象案件に紐づく直近 6 件）。
- 「既存の画面で開く」「利用者の受付番号」（AI窓口由来のみ）。

## 4. 操作は既存処理を呼ぶ（二重実装しない）

| 操作 | 呼び出し |
|---|---|
| 担当開始 | `App.startWork(id)` |
| 解決記録 | `App.resolve(id)`（原因・手順・所要・備考・KB下書き・子案件の一括解決） |
| 記入例 | `App.fillResolution(id)` |
| 下書きを開く | `App.go('draft', id)` |
| 既存の画面で開く | `App.go('queue', id)` |
| 利用者の受付番号 | `UX.openTicket(ticketId)` |
| 引継ぎの引き受け | `POST /api/case-handovers/:id/claim`（既存の受信箱と同じ API） |
| AI に聞く（AI窓口由来） | `POST /api/ai/answer-case`（共有 PC 情報・AI 履歴を根拠） |
| AI に聞く（直接受付） | `POST /api/ai/answer`（承認済みナレッジを根拠） |

既存処理はフォームの入力 ID（`#q_as`, `#r_cause`, `#r_steps`, `#r_min`, `#r_note`,
`#r_kb`, `#r_child`）を読む。ブリッジは呼び出しの間だけ同じ ID の入力を
画面外に置き、値を渡してから削除する。業務ロジック（状態遷移・監査・下書き生成）は
既存実装のまま 1 か所に保つ。

> 注意: 既存画面の入力 ID を変更する場合は、このブリッジも合わせて更新する。

## 5. 権限

- 担当開始・解決記録は `me().role` が `staff` または `itadmin` のときだけ表示する。
- `approver` / `auditor` は閲覧のみ（担当開始・解決記録のボタンを出さない）。
- 未受領の引継ぎの「引き受ける」も `staff` / `itadmin` のみ表示する。
- 「AI に聞く」も `staff` / `itadmin` のみ表示する（承認者・監査担当は閲覧のみ）。
- 左ナビの「引継ぎ」は一般社員には表示しない（`me().role !== 'employee'`）。
- サーバ側の権限判定は既存 API のまま。UI の非表示だけに依存しない。

## 6. データと制約（重要）

- 既存のヘルプデスク状態を読む。**画面用のサンプル・デモデータは持たない**。
- 既存の引継ぎは、AI窓口（cowork）から引き継がれた案件と、ポータル等から直接受け付けた案件がある。
  - AI窓口由来: `coworkTicket` / `coworkShared` / 会話 / 提案を表示できる。
  - 直接受付: 既存の引継ぎメモ・AIログ・監査を表示する。端末共有情報は「なし」と明示する。
- **解決ループ（Skill / verify / 新しい承認ハッシュ）はこの画面に未接続**。
  既存のヘルプデスク案件は従来フロー（AI相談 → 引継ぎ → 解決記録）のデータを持つため、
  Skill / verify を偽って表示しない。接続する場合は別途設計する。
- AI 質問の保存先: AI窓口由来の案件は `/api/ai/answer-case` が引継ぎスナップショットの
  チャットに質問と回答を保存する。直接受付の案件は `/api/ai/answer` のため保存されない。
- 表示と入力の区別: 入力用カードは背景色を変え、入力欄は白背景＋濃い枠、
  見出しに「入力」「表示」タグを付ける。読み取り専用のメモ・本文・会話は白背景のまま。
- 引継ぎの引き受けは、既存の受信箱と同じく成功後に画面を再読み込みする
  （cowork 状態のマージを確実に反映するため）。
- 画面を開いたまま既存画面で操作した場合は `aihd-state` イベントで再描画する。
- モバイル最適化は対象外（デスクトップ 1280px 以上を想定。1120px 以下で右ペインを隠す）。

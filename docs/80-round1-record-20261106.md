# 80. Round 1 記録（2026-11-06 / CTO バッチ実行）

## Round 1 の対象と受入条件

**対象**: AI HelpDesk の Staging 実態を実測し、独立 Staging を構築して本番昇格の前提を揃える。10 項目単位のバッチを 2 組実行する。

**受入条件（Round 1）**:

1. 稼働環境（service / 公開経路 / DB / backup / 監視）を read-only で実測し、未確認を明示する。
2. main の品質ベースライン（typecheck / lint / build / 全テスト）を隔離環境で実測する。
3. 他リポジトリ連携の契約と到達性を実測する。
4. 独立 Staging の設計を作る。
5. 独立 Staging のローカル実体（専用 DB・不変 release・専用 unit）を作り、稼働と health を実測する。
6. 本番に変更が及んでいないことを不変量で示す。
7. 通常変更は独立レビュー + CI + 差分確認のうえ自動マージする。
8. 復旧可能性（backup からの復元）を実測する。

## 仮説

- 現行は「本番相当 1 環境」で、独立 Staging が無いことが最大のギャップである。
- したがって、**本番の名前空間（unit/port/DB/tunnel/設定）に一切書かずに**、別クラスタ・別ポート・別 unit・不変 release で Staging を作れる。
- 品質は既に高く（CI green、全テスト pass）、本番昇格の障害は「環境分離と配備単位」にある。

### 初回 deploy で発見した不具合（修正済み）

1. `[ "$path" -f ]` の引数順誤り。
2. `npm prune --omit=dev` 後に devDependency の `tsx` で migration を実行していた（prune 前へ移動）。
3. health の `commit` が空で rollback 発火 → `release.env` に `COMMIT_SHA` を生成。**空 commit を成功扱いしないことを実証**。

## Blocker

- **承認プロンプトが無効なセッションのため、`systemctl` によるサービス定義変更・起動・再起動が自動拒否される。** 迂回せず、人間の番号選択を待つ。
- 対象: R-1 / R-2 / R-3 / R-4 / R-8。

## 次の行動（Round 2 の候補）

1. 承認が得られた範囲を順に実行（R-1 → R-2 → R-3 → 受入 → R-4）。
2. 承認不要の R-5（role 分離・release read-only 化）を先に実装して PR。
3. 監査ハッシュ鎖の復元後検証（R-6）を staging drill で実施。
4. 承認が得られない場合は、証拠の拡充とリスク評価を継続し、本番昇格は行わない。
